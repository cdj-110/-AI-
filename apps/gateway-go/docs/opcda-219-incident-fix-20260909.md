# 219 OPC DA 异常积累排查与修复

## 范围

首轮排查仅测试网关 `192.168.1.219`。OPC DA 服务端为 `192.168.1.100`。
首轮不修改采集配置、不清空异常数据库、不部署到 EG100；后续用户授权操作见下节。

## 已核实的现象

- 异常记录有 10,000 条，是 `internal/collectdiag/store.go` 的保存上限。
- 初始快照中 OPC DA 占 9,910 条；其中 8,931 条错误为
  `code=180 ... SyncRead requires a connected IOPCSyncIO association`，涉及 89 个点位。
- 同时存在 RPC 响应验证失败、连接超时、连接关闭及少量 S7/OPC UA 异常。
- 同一连接上的多个点位同时失败，随后 1～2 秒恢复；多次故障相隔约 6 分钟，
  但并非每个周期必现。不能把 10,000 条记录理解为 10,000 次独立连接中断。
- 旧服务并没有持续崩溃重启；异常记录确实反映采集失败，不是单纯页面重复渲染。

## 代码修复

1. 补齐 DCOM 对象生命周期登记和定时续租：ComplexPing 登记需要保活的 OID，
   每 60 秒 SimplePing；引用变化时更新集合，断开时尽力删除集合。
   按 SORF_NOPING 排除无需保活的引用。请求复用现有认证及完整性保护。
2. 保活与读取、浏览使用同一会话锁，避免 RPC call ID / NTLM 签名序号并发冲突；
   关闭和重连时停止、唤醒并回收保活线程。
3. 修复 OPC 数据解析失败误置整个会话为 FAULT：保留可用连接，允许上层拆分批次，
   将不支持的数据定位到具体点位。真正的传输或安全验证失败仍走重建连接流程。
4. 增加连接首个失败原因和保活结果日志，避免只看到后续 180 错误。
   后台线程更新错误时，错误文本接口提供独立快照，避免读取失效字符串。

缺失生命周期保活与周期性失效高度吻合，但旧日志不足以证明所有历史故障都是该原因。
解析失败错误关闭会话则已通过回归测试复现并修复。网络超时仍应保留并如实记录。
