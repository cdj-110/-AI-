# EG100 DL/T 645 超时诊断（只读）

## 结论

已用现场收发报文、异常记录和源码对齐，确认至少一次 P02 的 `context deadline exceeded` 是等待共享串口时外层采集预算耗尽，P02 本轮请求未发出。不是 P02 收到报文后 BCD / 实际类型解析失败。

本轮未改现场配置、未主动采集/写电表、未停服、未部署新程序。使用正常 Web 登录读取既有报文缓存，通过 SSH 只读核对配置与 SQLite 异常记录。

## 现场参数

- 设备 device-006，串口 /dev/ttyS2，9600 / 8N1。
- 表地址 010000000000，自动版本；有效请求为 2007。
- P01 DI 00000000；P02 DI 00000001。
- 通道同时存在 collectIntervalSeconds=10、collectIntervalMilliseconds=1000。代码优先使用毫秒字段，实际周期为 1 秒，不是 10 秒。
- 电表单次响应超时 1500ms，失败重试 1 次；设备重连等待 30 秒。

## 代码路径

- `internal/runtime/runtime.go`：collectPointSet 在执行点位前创建整轮 context；collectTimeout 对 1 秒周期返回 1 秒；collectTimeoutForPoints 目前只为 IEC 61850 扩展预算，DL/T 645 未扩展。
- `collectPoints` 把 DL/T 645 两点作为独立并发任务启动。
- `internal/collector/dlt645.go`：transactDLT645 使用同一串口 bus.mu 串行收发；等待互斥锁的时间消耗调用方 context。
- exchangeDLT645 获取串口锁后先检查 ctx.Err；若已过期直接返回，连 TX 报文都不会记录。这与 P02 本轮没有 TX、紧跟 P01 RX 后登记超时相符。
- 串口 Read 返回后可以先处理收到的有效帧，再进入下一次 context 检查，所以 P01 可以正常完成，P02 却拿到已过期的 context。
- 失败统一进入约 30 秒退避，因此一次慢响应会放大为另一点较长时间 BAD。

## 归因边界与修复方向

明确的问题在网关：整轮周期预算与总线排队/单帧响应预算混用，造成未发送的点位被当作采集失败。现场链路确有响应延迟波动，是触发因素；仅网关侧记录无法进一步断言 1.3 秒延迟全部来自 EMS、USB 驱动还是系统调度，需 EMS 侧同时间收发日志定位。

建议按串口总线串行调度、区分排队取消与设备响应超时，并按点位数量及重试预算计算整轮期限；排队取消不应关闭健康串口或进入设备断线退避。补齐队列等待、实际收发耗时和取消阶段记录。单纯调大电表响应超时不能解决外层提前取消。
