# 授权、安全与审批边界
版本：1.0.1｜现状证据与拟采用规则分别列示

## 已确认的项目文档规则
S-13 规定平台使用 Ed25519 私钥签发，网关只持公钥；授权绑定 HardwareId、RJGT102 USID、设备身份与功能。无效授权进入维护模式，不启动业务。
严格模式依赖生产构建注入公钥和强制开关；开发构建默认不强制。因此“文档存在”不能证明在用固件已启用。
v2 包含 keyId/licenseSequence，设备记录最大序号和签名摘要，同文件可重复导入，较旧序号/同序号不同载荷拒绝；首次接受 v2 后拒绝 v1。私钥、独立设备凭据加密密钥与轮换流程见原项目文档，包内不复制密钥。
软件状态不能抵御 root 删除、整盘回滚或替换程序。文档明确安全启动、可信单调计数器、时间防回拨与在线吊销不在该阶段完整实现范围。
S-14：.lic 是文件扩展名，内容仍为 JSON，安全来自签名校验。
S-15：后端需同时校验租户、功能权限和设备范围；前端隐藏按钮不能作为安全边界。
S-16：成员停用与设备云连接停用独立；恢复租户不应恢复设备单独禁用。历史记录中的 EMQX 管理密钥角色为 administrator，不是细粒度仅断开权限。

## AI 研发权限草案
- 知识管理员/规划者：读取已授权资料、生成事实与任务，不获取生产秘密。
- 开发者：在隔离工作区修改允许文件、测试合成数据；不直接合并或发布。
- 审查者/QA：独立检查需求、差异和执行证据，不能以开发者自报成功放行。
- 发布准备者：形成固定提交、制品摘要、配置版本、迁移和回滚清单。
- 人工负责人：审核实际候选、批准合并/生产执行；具体审批身份和平台门禁尚未配置。

建议的流程为：任务与验收 → 开发 → 独立测试和审查 → 发布候选 → 人工批准 → 受控执行。高风险任务可以先完成方案、代码和隔离验证；真实设备/生产写操作依赖专项授权。审批内容变化后重新批准，不能让 AI 更改门禁并自批。

审批应绑定仓库、提交、制品摘要、目标环境、配置/迁移版本和回滚方案。文档规则不是技术隔离；需在后续实现身份权限、受限执行器及可追溯日志，不以 roles.draft.json 本身宣称安全门禁已生效。

## 待确认的安全验收
- 在用包的强制开关、公钥环、授权 v1/v2 兼容和设备恢复演练。
- MQTT 身份与 topic ACL、跨租户订阅、子设备归属、防重放与设备转移。
- OTA 签名、版本防回滚、失败恢复；不能因授权文件已签名而推断 OTA 已签名。
- 远程维护和控制的操作者权限、超时、幂等、审计；S-20 的任务受理状态不等于执行完成。
- 默认开发凭据/模拟验证码是否进入生产、Compose 浮动镜像是否已锁定；本包不转录任何凭据值。
- 依赖许可证与第三方原生库使用范围，待组织审阅；本次不提供法律合规结论。
