# 边缘计算当前值浮点尾数修复

## 根因链路

1. Modbus RTU/TCP 共用 `mapper.Decode`，寄存器原始值 438 乘倍率 0.1，在自动精度模式下产生 float64 的 `43.800000000000004`。这是二进制浮点表示误差，不是额外采到的数据。
2. Store 保存采集结果，供计算、告警及转发使用；边缘计算 Preview 和运行时表达式读取该数值。加上 16 后结果为 `59.800000000000004`。
3. 之前只在 MQTT 传输及普通点位表格做了尾数处理。REST 状态、WebSocket 快照/增量、试算响应仍携带原始长尾；边缘计算页面直接 String/JSON.stringify，且未应用派生点显示小数位。

## 本次修复

- 抽取已有 MQTT 保守尾数处理为 `internal/valueformat`，REST、WebSocket 和试算响应复用。只压缩距离不超过两个 float64 相邻步长、且至少减少四位有效数字的冗余尾数，不统一截断真实高精度数据。
- JSON 序列化时处理副本；不修改 Store、CEL 输入、计算顺序或协议写入逻辑。不改变各协议原有的采集倍率及小数位处理。
- 边缘计算输入当前值使用来源点显示精度，实时/试算结果使用派生点显示精度；试算输入摘要也统一格式化。
- 前端自动精度沿用同一保守规则，保留 bool、精确整数文本和字符串语义。两位显示精度下例子结果为 `59.80`。

## 验证

- 实际 Modbus 解码 0x01B6 → 438 × 0.1 → Store → 全量/筛选 REST → CEL 试算接口，断言 43.8 和 59.8，并验证内部原始精度不变。
- WebSocket 初始快照和 points.diff 使用同一规范；布尔值、大整数、字符串、数组及高精度数值回归。
- 原有 MQTT 各负载模式、随机精度边界与不变性测试继续通过。
- 前端数值显示回归、类型检查及生产构建通过。
